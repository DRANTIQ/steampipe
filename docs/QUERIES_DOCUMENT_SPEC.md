# Queries Document — Format and Apply to `queries` Table

This doc defines the **queries document** format: a single file that lists all queries to be applied (upserted) into the `queries` table. Use it for seeding, import, or CI.

**Current subset:** We implement **17 queries** for now (see `data/queries.json` and [QUERIES_CATALOG.md](QUERIES_CATALOG.md)). More can be added later by editing the document and re-running the apply script.

---

## 1. Document format (JSON)

**File:** `data/queries.json` (or `docs/queries_applied.json`).

**Structure:** One JSON object with a key `queries`: an array of query objects. Each object maps to the `Query` model.

| Field | Type | Required | Default | Notes |
|-------|------|----------|---------|------|
| name | string | yes | — | Unique with `version`. |
| version | string | yes | "1.0" | |
| provider | string | yes | — | e.g. `aws`. |
| plugin | string | yes | — | e.g. `aws`. |
| query_text | string | yes | — | Steampipe SQL (Postgres-style). |
| execution_mode | string | no | "single_account" | |
| output_format | string | no | "json" | |
| schedule_enabled | boolean | no | false | |
| active | boolean | no | true | |
| extra_metadata | object | no | null | framework, control_ref, category, required_columns, pass_rule, source. |

**No `id`** in the document — the apply step generates UUIDs for new rows. Identify existing rows by `(name, version)` for upsert.

**Example entry:**

```json
{
  "name": "s3_buckets_versioning_disabled",
  "version": "1.0",
  "provider": "aws",
  "plugin": "aws",
  "query_text": "select name, region, account_id, versioning_enabled from aws_s3_bucket where not versioning_enabled;",
  "execution_mode": "single_account",
  "output_format": "json",
  "schedule_enabled": false,
  "active": true,
  "extra_metadata": {
    "category": "compliance",
    "framework": "CIS AWS Foundations 4.0",
    "control_ref": "s3-versioning",
    "required_columns": ["name", "versioning_enabled"],
    "pass_rule": "zero_rows"
  }
}
```

## 2. How to apply the document to the `queries` table

**Option A — Apply script (recommended)**  
Run:

```bash
python scripts/apply_queries_document.py
```

The script (`scripts/apply_queries_document.py`):

1. Loads `data/queries.json` (override with env `QUERIES_JSON_PATH`).
2. For each entry: look up by `(name, version)`. If found → update `query_text`, `provider`, `plugin`, `extra_metadata`, etc. If not found → insert new row (UUID generated by model).
3. Uses `DATABASE_URL` (or `SEED_DATABASE_URL` for a separate seed DB). Does not delete rows that are not in the document.

**Option B — API**  
Call `POST /api/v1/queries` for each entry (creates only; no upsert unless you add a dedicated import endpoint).

**Option C — SQL**  
Generate `INSERT ... ON CONFLICT (name, version) DO UPDATE ...` from the JSON (migration or one-off script).

We use **Option A** so one run of the script applies the full queries document.
